# Fawkes: proposed revised roadmap

**8 September 2026 · Proposal grounded in the verified repository export**

**Revision:** Tanner has clarified the physical product direction: build our own progressively more capable Fawkes bodies throughout software development. Enjoyable interaction and hands-on learning are explicit outcomes. Historical robot names are references, not a prescribed platform sequence. The immediate P5 runtime scope is unchanged.

This document changes proposed sequencing, acceptance evidence, and near-term scope. It preserves the Phoenix purpose, the numbered 0–39 capability spine, source/interpretation separation, rider authority, historical provenance, synthetic isolation, and exclusive same-Phoenix continuation. It does not edit the canonical roadmap or authorize implementation, spending, messaging, personal-history ingestion, deployment, or autonomy.

Read **Fawkes-Repository-Assessment.md** for the evidence and limits behind finding IDs F01–F14.

## The revised goal for the next stretch

Deliver a console Tanner can actually use, prove one bounded development campaign through the real owners, and make personal continuity dependable enough for the already-defined Tanner Alpha trial.

These are three distinct outcomes. A usable read-only console does not depend on every personal-AI feature. A successful coding pilot does not certify personal Memory. Neither closes mature autonomy, embodiment, multi-rider support, or the entire roadmap.

The long-term idea stays ambitious. The immediate work becomes smaller and observable.

## Changes to the accepted sequence

The current canonical pre-Phase-10 order is supervision → bounded cleanup → post-cleanup audit/regression/recovery/baseline → social messaging → recording/privacy → numbered-roadmap resumption.

I propose these specific amendments:

1. **Give read-only console delivery its own early exit.** It completes part of Rider supervision and can proceed before a live development pilot. It must neither mutate authority state nor pretend to be observing a heartbeat it does not have.
2. **Use the existing pilot to exercise a small real end-to-end slice.** Correct demonstrated application contract mismatches and test cancellation/restart boundaries first. Do not add a new orchestration or sandbox migration.
3. **Make continuity and release repairs explicit bounded cleanup objectives.** Group them by one causal boundary each; do not turn all findings into one giant campaign.
4. **Move recording/privacy before broader personal or social capture.** A user-facing private mode must apply to traces and queued derivatives as well as Archive writes.
5. **Move two-way/proactive social messaging out of the serial prerequisites to personal Alpha.** Preserve it as a separately authorized track after its recording, recipient, channel, and delivery conditions hold. This is a proposed amendment to an explicit existing order, not a claim that the old document already allows it. Existing operational notifications retain their own grants.
6. **Place prospective native continuity explicitly before counting lived Alpha evidence.** Implement only the missing current trust boundary; mature portable migration remains Phase 34.
7. **Replace duplicate immediate checklists with one current pointer.** Keep old evidence as dated history. A document should say whether a feature is implemented, qualified, integrated, deployed, or actually used; those words are not synonyms.

No source-integrity, consent, or continuity rule needs to be relaxed to make these sequencing changes.

## Work packages and exit criteria

### A. Finish P5 and show the actual console

**Purpose:** give Tanner the first useful visible endpoint now that P1–P4 are integrated.

**Dependencies:** current integrated base and the preserved P5 postimages/evidence. No live autonomy, personal-history ingestion, or physical enclosure is required.

**Scope:** the existing P5 files, the canonical Attention observational interface, the Chat service forwarding path, authentication/activity separation, and directly responsible tests. A complete owner boundary is the scope; an arbitrary file-count ceiling is not the design.

**Required behavior:**

- Repeated authenticated GET/polling does not persist Attention lifecycle changes or mark a person active merely because a device polls.
- Expired requests appear unavailable based on observation time. Actual mutations still check current canonical eligibility.
- The existing fixed header, four pages, swipe behavior, idle return and square layout remain.
- Refresh preserves reading position, expanded details and selected identity. Wheel-click must operate on the visible current record.
- Component values distinguish observed, stale, unavailable and configured state. Hardcoded `READY`/`IDLE` values are not presented as measured liveness.
- Approval continues through the existing native route. No new console-owned decision API or GPIO authority.

**Exit evidence:** a real-dependency HTTP fixture with protected-store before/after comparisons, targeted interaction regression, existing required candidate acceptance, and a working local preview inspected by Tanner at 720×720. Do not require browser automation; deterministic interaction tests and explicit manual device checks can establish the relevant claims.

**Non-goals:** richer code browsing, live campaign creation, hardware firmware, sound redesign, full architecture visualization, or personal-AI repairs. Those do not block this first view.

**Stop:** if the endpoint can only be made “read-only” by bypassing authentication, ignoring expiry on mutation, or deriving authority in the browser, retain the candidate and fix the canonical seam. A stopped or stale service must be visible, not simulated as live.

### B. Prove the general campaign path, then run one batch

**Purpose:** establish useful bounded development autonomy through the owners already implemented.

**Dependencies:** a reproducible disposable material baseline, canonical condition/scope semantics, and satisfactory application interruption tests. The first read-only console can already be used while this work proceeds.

**Corrections:** address F08/F09 using one condition-identity representation and one repository-exclusion contract. Reproduce F10 before deciding its patch. Bind the runner's repository to the canonical owner before action. Preserve old receipts and completed invocations; no retroactive normalization of their meaning.

**Composed zero-provider exit:** use actual campaign/application/Git owners in a disposable repository, with provider outputs supplied by a clearly synthetic fixture. The request must contain conditions in a different order, two authorized files with only one changed, a real retained diff, and exact expected parent. Verify one application, one commit, and inert terminal replay. Also inject cancellation before mutation and interruption during application; verify no unauthorized new mutation and correct reconciliation after expiry. Do not replace all owners with a fake `succeeded` transition.

**Live pilot:** after the fixture and existing qualification pass, rebind the inert pilot specification and obtain the separate exact start authorization. Use one small non-production objective, one batch, fixed limits, an explicit stop boundary, retained results, and no remotes or production promotion unless separately authorized. Observe it on the console if A is ready; the normal existing interface remains available otherwise.

**Exit evidence:** completed objective or honestly classified bounded stop; exact receipts; budget/reservation closure; application and commit counts; no replay; measured provider processing, human wait and interruptions. A deterministic refusal is a useful negative test but is not the successful pilot exit.

**Non-goals:** perfect provider recovery, unlimited retries, additional workers, Temporal/DBOS/Restate migration, Inspect replacement, a new authority tier, or LangGraph deletion.

**Stop:** ambiguous provider completion, invalid lineage, out-of-scope change, stale binding, exhausted budget, cancellation or expiry at a new effect, or inability to reconcile an existing operation. Preserve already consumed attempts; do not retry them under a new name automatically.

### C. Establish a reproducible operational baseline

**Purpose:** stop repeating mixed-import, missing-environment, state-root and release-selection failures.

**Dependencies:** can proceed alongside A; feeds B where the pilot needs a clean material baseline and feeds production use before deployment.

**Scope:** existing setup/release/service tooling, explicit runtime/dependency inputs, material-source provenance, and relevant tests. Treat the 127 historical paths as classified input. Integrate necessary unfinished dependencies in small logical groups with their own provenance; do not mass-stage them, delete them, or quietly use private production stores as test fixtures.

**Required behavior:**

- A documented disposable command reconstructs the required source and dependencies without relying on unlisted paths in Tanner's checkout.
- Qualification uses an explicit writable external state/temp root with adequate resources, then removes temporary candidate links before freeze.
- Unexpected background-thread failures fail the qualification result; expected error fixtures remain distinguishable.
- A release's code and dependency environment are prepared and validated before selection, and rollback selects the matching pair.
- Production startup validates state locations and the intended instance. Missing continuity state is a recovery condition rather than silent default-instance creation.
- Privileged controls are either proven through an appropriately narrow supported route or clearly unavailable. Do not weaken web-process hardening to make an unsupported button work.

**Exit evidence:** source reconstruction inventory, clean import/test execution, race-sensitive migration result, copied-state restart/restore test, dependency-aware release/rollback proof, and a precise implemented-versus-deployed status record in existing documentation.

**Non-goals:** new deployment platform, cloud state service, generalized privileged command runner, or a second release ledger.

### D. Repair personal continuity as bounded cleanup

**Purpose:** make ordinary source retrieval and Memory trustworthy under retry, change, restart and correction.

**Dependencies:** consistent state-root configuration from C. These repairs can be manually implemented and qualified while B is being prepared; building reliable Fawkes does not require Fawkes to repair itself first.

Implement these in dependency order, as separate small causal changes:

1. **Source identity and reconstruction:** reject changed-payload/owner replay; preserve original bytes; project only validated source content; scope revisions by owner before grouping; separate original turn order from revision capture time. Prove alternate-root ingest → revision → rebuild equivalence.
2. **Memory mutation and recovery:** validate ownership consistently; make evidence application idempotent; reconcile the whole supersession/event/ledger operation. Inject interruption at each durable boundary. Same evidence must not become stronger by being retried.
3. **Model-visible truth:** carry useful uncertainty, source era and conflict/temporal qualification into rendered context. Test the exact provider-visible package and resulting bounded behavior, with appropriate synthetic labeling.

**Exit evidence:** original hashes unchanged; rebuilt projection equivalent; cross-owner source IDs isolated; earlier edited turns stay in the correct sequence; supersession recovery leaves the intended active records; duplicate evidence inert; contradictory/changing preferences remain visibly qualified; fresh sessions retrieve eligible evidence without reviving permissions.

**Non-goals:** semantic embeddings as a cure for provenance, a replacement Memory database chosen in advance of the fix, full Phase 11 temporal knowledge, full Phase 12 Claim Ledger, mature relationship/personality systems, or bulk historical absorption.

**Stop:** any unexplained source mismatch, owner confusion, partial mutation falsely marked complete, synthetic/native contamination, or need to rewrite originals to obtain consistency.

### E. Close the remaining pre-Alpha trust obligations

**Purpose:** satisfy the existing meaning of daily personal Alpha.

**Dependencies:** C/D; the existing stabilization gates; independently authorized source ingestion if the real export remains unstaged. Console availability and a physical shell are not prerequisites.

**Recording:** one authoritative interaction-retention decision must cover Archive, Memory candidates, Flight/context traces and attachment derivatives. A private-mode test searches every applicable store after the turn. Disable or bound features that require audit retention the Rider declines. Previously retained history is not deleted merely because future recording is paused.

**Prospective native continuity:** bind the intended Phoenix and lineage to the authorized writer and ordered commits before counting new interactions as native lived history. Under the bounded single-host deployment, prove exclusive writer admission and restart behavior; restoration must not activate a second authoritative continuation. Never relabel founding history retrospectively. A copied test dataset remains an inert/synthetic fixture, not another active Phoenix. Full portable continuity tooling remains a later phase.

**Real history:** if still outstanding, obtain the explicit source/owner/retention authorization for the selected Tanner export, stage exact originals as inherited/founding evidence, validate coverage and anomalies, and manually inspect representative original-linked results. Actual corpus qualification remains distinct from the fourteen synthetic native scenarios. Automatic historical absorption stays Phase 13.

**Workshop foundation / Phase 10:** use existing Exchange and Development evidence to preserve a failure, investigate it, and produce an inert, attributable improvement proposal for Human Review. No new message bus or self-application. This audit can supply concrete investigation inputs; it does not become Fawkes's autobiographical experience by being imported into a task.

**Exit evidence:** consistent ownership/recovery; tested personal recording behavior; prospective continuity proof; validated permitted history; actual rendered-context evidence; and one non-self-applying Workshop proposal. Apply the existing exact-change acceptance process to changed code. Do not commission another generic full-repository audit merely because this one found work.

### F. Run the defined seven-day Tanner trial

**Purpose:** test whether the personal-AI foundations are useful and trustworthy in real use.

**Dependencies:** E and the remaining applicable Phase 0–10 trust obligations. Tanner remains the only real Alpha Rider.

Use the already-defined desktop/iPhone trial: ordinary conversation, Library, research, source-linked history search, continuity across sessions, correcting an interpretation, provider failure, restart and backup/restore, retrieval feedback, and one Fawkes-generated improvement proposal. Include meaningful mundane and relational context selected by Tanner, not just code and contrived benchmarks.

**Exit evidence:** no canonical data loss, owner leakage, invented success or silent protected change; recoverable failures; corrections have the intended future effect without falsifying the past; and recorded examples of actual usefulness. Track unwanted interruptions and manual repair burden. Seven elapsed days with no meaningful usage do not prove the trial.

This is the existing real-use duration, not an estimate for how long engineering will take. Later features continue after Alpha; Alpha does not mean the whole vision is finished.

## Progressive physical embodiment throughout the roadmap

**Build our own Fawkes bodies early, learn from using them, and make them more capable as the software matures.** A simple body should be enjoyable and useful in its own right. Each iteration teaches us about expression, mechanics, power, maintenance and interaction, contributing to the mature bird/phoenix-like companion Tanner sees as a potential major product differentiator. Market appeal remains a hypothesis to validate, not an established outcome.

These are capability milestones, not five mandatory purchases or complete chassis replacements. Improve the existing body when sensible. The console remains the current supervision device; the in-app true-3D Phoenix remains Early Presence. Neither replaces this physical robot track. Each connected body is a genuine form of the same Fawkes, with continuity owned by the existing core and no second authoritative Phoenix.

## What moves off the immediate critical path

- Replacement workflow engines or Reviewer frameworks.
- A new universal identity mega-object. Fix the shared condition/scope contracts actually shown to disagree.
- A new content-addressed platform. Reuse retained evidence and eliminate proven duplication without losing resolvability.
- Perfect automatic provider-result recovery. Preserve conservative bounded ambiguity handling.
- Mature Ghost Rider populations, decade-length claims, a permanent mandatory Challenger, and general model routing.
- Full code graph visualization, showcase mode, public-site polish, mature voice/video, home integration and mature autonomous physical agency. Early bounded physical prototypes remain on the parallel embodiment track.
- Bulk historical absorption or automatic personality change.
- A second approval endpoint for the console or a broad bootstrap authority tier.

These items remain available future decisions where already in the vision. They are not the price of seeing the console or closing one useful batch.

**Recovery and assurance:** use existing receipts and canonical owners. This report supplies findings to the current stabilization work. Future source changes still satisfy their applicable exact acceptance conditions; no new perpetual meta-review process is added.

## How to measure progress without misleading estimates

For each completed batch, retain provider turns and token usage where available, qualification duration, provider-processing duration, human-decision wait, number of substantive interrupts, and whether the intended result actually completed. Reuse existing records; do not build a new analytics platform.

Use those measurements to estimate later similar work. No fixed date for this sequence is supported by the export. The seven-day trial is the established real-use gate, not seven days of coding. A large test count, a safe stop, an integrated commit, or a beautiful rendering each proves a different thing; none substitutes for all the others.

This proposal changes documents only. It creates no live authority, no new native history and no autonomous session.
