## Native approval authority and adoption

`NativeApprovalRelay` uses the installed, hash-pinned official Codex 0.153.4
private Unix WebSocket. Peer UID and executable identity are checked. It reads
the exact already-loaded Worker and rejoins that same thread using
`thread/resume` with `excludeTurns`, without a prompt, model/config override,
new turn, new account or global permission change. The existing independent
Reviewer route is separate and unchanged. Protocol meanings are checked against
the installed generated schemas and [official app-server documentation](https://learn.chatgpt.com/docs/app-server).

Only the demonstrated `item/commandExecution/requestApproval` command form is
accepted. Complete command, working directory, timestamp, thread/turn/item IDs
and the server's offered decisions must validate before display and again before
response. Reason text is labeled Worker-stated, not verified safety. Unknown
action kinds, network/additional-permission overlays or new decision shapes
remain visibly unsupported and must be answered on the PC.

Each offered decision retains its original order and exact native value.
Approve-once, deny, cancel and session approval are not substituted for one
another. A proposed persistent execpolicy choice shows its full exact token
prefix and continuing scope; selecting it requires a separate explicit confirm.
The native session cache's undisclosed matching semantics are labeled unknown.

Authenticated same-origin, session-CSRF-protected HTTP accepts only the exact
request/action/choice/submission identities, never arbitrary commands or chat
text. A single reader owns the connection's native IDs and drains received PC
resolutions before sending a queued Pi response. Codex arbitrates any remaining
simultaneous PC/Pi race. A resolution notification does not identify the winning
choice and is not execution success. Operation results are recorded separately.

Private atomic audit records and a per-thread ownership lock preserve selection
history. Intent is recorded before response, with a maybe-sent barrier; failed
or restarted connections never replay a decision. Duplicate submissions return
their original identity or reject conflict. Connection epoch, action digest,
fresh synchronization and the current pending ID are rechecked at send time.
Expired local response windows are not described as native request expiry:
the pending card directs Tanner to the PC until Codex resolves the request.
Unsupported, missing, stale and disconnected queues are not confirmed empty.

Only the newly accepted launch configuration may enable this relay alongside
the same-thread conversation owner on the accepted port-8790 service. A
development fixture, rollback service or unaccepted source must not enable it
against the real Worker. Independent review must cover this adoption wiring and
the preserved authentication/permission boundaries, not just the visual card.
